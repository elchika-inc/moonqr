# 混在モードのセグメント最適化（設計）

- 日付: 2026-07-29
- 対象: `core/src/encode/`（エンコーダのみ。デコーダは変更しない）
- 前提: v0.1.0 公開済み。README の Limitations に「混在モードのセグメント最適化なし」と明記されている状態

## 背景

現在のエンコーダは `detect_mode` で**入力全体に1つのモード**を選ぶ。1文字でも小文字が混ざれば全体が Byte モードになり、その中に長い数字列があっても 8bit/文字で符号化される。

ISO 18004 は1つの QR に複数のモードセグメントを並べることを認めており、区間ごとに最適なモードを選べば同じ内容をより少ないビット数で表現できる。

### なぜこれを Phase 4 に選んだか

Phase 4 の候補は3つあった（漢字モード encode / 混在モード最適化 / ECI・Structured Append）。混在モード最適化を選んだ理由は次の2点。

**1. バンドルサイズを増やさない。** 漢字モード encode には Unicode→Shift-JIS の変換テーブルが要る。デコーダは既に `core/src/decode/sjis.mbt`（141 KB・7037 エントリ）を持つが、これは decode 側の閉包にあり、`/encode` サブパス（21.3 KB raw / 6.4 KB gzip）には含まれない。encode 側に同等のテーブルを持ち込むと、Phase 3 Task 3 で `core-encode.ts` / `core-decode.ts` を分けてまで実現した「encode だけ使う人は decoder を1バイトも取り込まない」という設計が壊れる。混在モード最適化はテーブルを必要とせず、アルゴリズムだけで完結する。

**2. デコーダを変更しなくてよい。** 複数セグメントの読み取りは Phase 2 で実装済みであり、jsQR の e2e コーパス 214/214 を通している時点で、実世界の混在モード QR を既に読めている。この Phase は「デコーダが既に読める形式をエンコーダも出せるようにする」作業であり、新しい形式を導入しない。リスクがエンコーダ側に閉じる。

### 効果の実測（2026-07-29）

qrcode npm（最適化を行う）と現在の moonqr（単一モード）で、同じ入力に対する最小バージョンを比較した。EC レベルは M。

| 入力パターン | 長さ | moonqr | qrcode | 差 |
|---|---|---|---|---|
| `https://ex.com/id/` + 数字5桁 | 23 | v2 | v2 | 同じ |
| `https://ex.com/id/` + 数字10桁 | 28 | v3 | v2 | **-1** |
| `https://ex.com/id/` + 数字15桁 | 33 | v3 | v2 | **-1** |
| `https://ex.com/id/` + 数字20桁 | 38 | v3 | v3 | 同じ |
| `https://ex.com/id/` + 数字30桁 | 48 | v4 | v3 | **-1** |
| `https://ex.com/id/` + 数字40桁 | 58 | v4 | v3 | **-1** |
| `https://ex.com/id/` + 数字60桁 | 78 | v5 | v4 | **-1** |
| `https://ex.com/id/` + 数字100桁 | 118 | v7 | v4 | **-3** |
| `注文番号は` + 数字30桁 + `です` | 37 | v4 | v3 | **-1** |
| `注文番号は` + 数字60桁 + `です` | 67 | v5 | v4 | **-1** |
| `HTTPS://EX.COM/ID/` + 数字60桁 | 78 | v4 | v3 | **-1** |
| 数字のみ・英数字のみ・短い混在 | — | — | — | 同じ（既に最適） |

効果があったのは 14 ケース中 9 ケース。最大で 3 バージョンの縮小（v7 → v4、モジュール数では 45×45 → 33×33 で面積比 約 1.9 倍の差）。

**効果が出る条件**は「Byte モードに落ちる文字を含み、かつ長い数字列を持つ」入力である。URL に長い ID が付く形、日本語の文中に注文番号が入る形が該当する。

### 表の読み方に関する注意（2026-07-29 追記・実装中に判明）

上表の「同じ」は**バージョンが変わらない**という意味であって、**分割の効果がない**という意味ではない。QR のバージョンは離散的なので、ビット数が減ってもその容量段階をまたがなければバージョンは変化しない。

実装中に独立計算で確認した実際の値（`https://ex.com/id/` + n 桁、v1 の文字数指示子で計算）:

| n | 単一 Byte | Byte + Numeric に分割 | 有利な方 |
|---|---|---|---|
| 1 | 164 bit | 174 bit | 単一 |
| 2 | 172 bit | 177 bit | 単一 |
| 3 | 180 bit | 180 bit | **同点** |
| 4 | 188 bit | 184 bit | 分割 |
| 5 | 196 bit | 187 bit | 分割 |

**分割が有利になる境界は 3〜4 桁の間**であり、上表で「同じ」と出た 5 桁のケースでも分割の方が 9 bit 小さい（両方 v2 に収まるためバージョン差として現れないだけ）。qrcode npm も 5 桁の時点で `[Byte:18, Numeric:5]` に分割している。

したがって「数字が短ければ切り替えない方が得」という性質は正しいが、その閾値は 5 桁ではなく 3〜4 桁である。テストで境界を固定する際は、単一が明確に有利な n=2 と、分割が明確に有利な n=5 を使う。**n=3 は同点なのでテストに使わない** — どちらを選んでも最適であり、固定すると実装の内部詳細を仕様化してしまう。

この境界の存在自体が、次節でアルゴリズムに貪欲法を採らない理由になっている。

## 決定事項

1. **アルゴリズム**: ランレングスに圧縮したうえで動的計画法。バージョン帯ごとに3回計算する。
2. **成功基準**: qrcode npm と比較し、**全ケースで同じか小さいバージョン**になること。1件でも負けたら不合格とする。
3. **API**: `encode(text, ec, version)` のシグネチャは変えない。最適化はデフォルトで有効。オプトアウトのフラグは作らない。
4. **スコープ**: 漢字モード・ECI・Structured Append は対象外。

## アルゴリズム

### ランレングス圧縮

素朴に全ての分割位置を探索すると入力長 n に対して O(n²) になる（Byte モードの最大長 2953 文字で約 870 万通り）。しかし**最適な分割の境界は文字種が変わる位置にしか来ない**。

- 数字列の途中で切って両側とも Numeric にするのは、切替コストが増えるだけで常に損である
- 逆に「数字列を前後の Alphanumeric セグメントに巻き込む」ことが得な場合はあるが、これは「複数のランをまたいで1つのモードで表現する」として DP が扱う

そこで、まず入力を文字種のランに圧縮する。

```
"https://ex.com/id/123456789012"
→ [Byte×18][Numeric×12]        ラン数 2
```

各文字は「その文字を表現できる最も制限的なモード」で分類する。モードの表現力には包含関係があり、Numeric ⊂ Alphanumeric ⊂ Byte である（数字は Alphanumeric モードでも Byte モードでも表現できる）。ラン数は実用的な入力では 2〜10 程度に収まるため、DP のコストは実質的に定数となる。

### 動的計画法

```
dp[j] = 先頭から j 番目のランまでを符号化する最小ビット数
dp[0] = 0
dp[j] = min over (i < j, mode) { dp[i] + segment_bits(ラン i..j-1, mode) }
```

`mode` の候補は、**区間 i..j-1 の全文字を表現できるモードすべて**である。モードの表現力は Numeric ⊂ Alphanumeric ⊂ Byte なので、区間に Byte でしか表現できない文字が1つでもあれば候補は Byte のみ、区間が数字だけなら Numeric / Alphanumeric / Byte の3つすべてが候補になる。

同一区間だけを見ればより制限的なモードの方が常にビット数は小さいが、候補から外してはならない。前後のセグメントと**同じモードに揃えることで切替コストが消える**場合、単独では不利なモードが全体最適になりうるためである（例: 英字・数字・英字と並ぶとき、数字部分を Alphanumeric に含めて1セグメントにする方が、3セグメントに分けるより小さくなる）。

`segment_bits(区間, mode)` はモード指示子 4bit + 文字数指示子（`cci_bits(mode, version)`）+ データ部の合計。データ部のビット数はモードごとに異なる。

| モード | データ部 |
|---|---|
| Numeric | 3文字ごと10bit。余り1文字は4bit、2文字は7bit |
| Alphanumeric | 2文字ごと11bit。余り1文字は6bit |
| Byte | 8bit/文字（UTF-8 バイト列の長さで数える） |

**端数の扱いがモードごとに違うため、「1文字あたりのビット数」に均して近似してはならない。** セグメントの文字数が確定した時点で正確に計算する。ランレングス圧縮によって区間が確定してから計算する構造になるため、これは自然に満たされる。

### バージョン帯

`cci_bits` はバージョン帯（1-9 / 10-26 / 27-40）でのみ変化する。したがって最適な分割は帯ごとに1つ定まり、**DP は3回で足りる**。

現在の `encode` は v=1..40 を線形試行して最初に収まったバージョンを返す。この構造は維持し、各 v ではその v が属する帯の分割結果を再利用する。

## 影響範囲

| ファイル | 変更 |
|---|---|
| `core/src/encode/segment.mbt` | ラン分解・区間ビット数の計算・DP・複数セグメントの書き込みを追加 |
| `core/src/encode/encode.mbt` | 単一 `write_segment` の呼び出しをセグメント列の書き込みへ変更 |

`detect_mode` は削除せず残す。単一モード判定として、ラン分類の部品になる。

デコーダ（`core/src/decode/`）と TypeScript ラッパ（`packages/`）は変更しない。

## API への影響

`encode(text, ec, version)` および JS 境界の `encode_js` のシグネチャは変更しない。

- デコード結果（テキスト）は不変
- 同じ入力に対してより小さいバージョンが選ばれうる（実測で最大 -3）
- `version` を明示指定した場合は指定を尊重する（従来どおり）
- 空文字は `None`、容量超過は `None` の既存契約を維持する

出力される QR の見た目が変わるため、semver は 0.2.0（minor）とする。

## 検証

| 層 | 確かめること |
|---|---|
| 最適性 | qrcode npm と比較し、全ケースで同じか小さいバージョンになること。1件でも負けたら不合格 |
| 正しさ（往復） | 生成した QR を自前デコーダと jsQR の両方で読み、元テキストと完全一致すること |
| 回帰 | 既存の160通り行列一致テスト（`version-sweep.test.mjs`）がそのまま通ること |
| 境界 | 分割が不利な側（n=2）と有利な側（n=5）を契約として固定すること。n=3 は同点なので使わない |
| ラン分解 | 包含関係を含む文字種分類が正しいこと（数字が Alphanumeric 区間に巻き込まれる場合を含む） |

### 既存テストが回帰検出になる理由

`version-sweep.test.mjs` の入力は `V1L`・`V40H` のような英数字のみの短い文字列であり、分割の余地がない。したがって最適化後も出力はビット単位で同一でなければならない。ここが変われば「分割すべきでない入力を分割した」バグの証拠になる。既存テストを変更せずにセーフティネットとして使う。

### オラクルの性質が従来と異なる点

これまでの Phase では qrcode npm と「bit 単位で一致」を基準にしてきたが、本 Phase では「qrcode 以下」という不等式で判定する。独自の DP が qrcode npm より良い解を出した場合も合格とするためである。qrcode npm の分割アルゴリズムは移植せず、出力の比較にのみ用いる。

## 実装しないもの（YAGNI）

| 見送るもの | 理由 |
|---|---|
| 漢字モードのセグメント | 変換テーブルが `/encode` のバンドルサイズを壊す。別途設計が要る |
| ECI / Structured Append | 実需要が確認できていない |
| 最適化のオプトアウトフラグ | デコード結果は変わらず、出力が小さくなることを望まない利用者は想定しにくい |
| 分割結果を外部へ公開する API | 内部実装に留める。公開すると semver の制約になる |
